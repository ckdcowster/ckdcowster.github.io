Review Best Practices

When you don’t fully know the context
  • “What upstream assumptions does this rely on?”
  • “What downstream behaviour depends on this?”
  • “What breaks if this returns unexpected data?”
When you’re unsure about syntax or idioms
  • “Is this the clearest way to express the intent?”
  • “Would a more explicit version be easier to maintain?”
  • “Is this relying on a trick that future maintainers may not know?”
When you’re unsure whether the code is too complex
  • Nested conditionals > 2 levels
  • Functions > 40 lines
  • Classes doing more than one responsibility
  • Ask: “Can this be simplified or split into smaller units?”
Separation of Concerns

Each part of the code should have one clear responsibility.

  • Ask: “Can this be separated into clearer layers?”
When you’re unsure whether naming is good
  • If you can’t guess what the variable means without reading the code, the name is wrong.
  • Ask: “Can this name be more descriptive?”
When you’re unsure whether comments are useful
  • Use the Why, not What rule.
  • Ask: “Can you explain why this logic exists?”
Error Handling & Failure Behaviour
  • Does the code fail loudly?
  • Does it avoid silent fallback?
  • Are errors actionable?
  • Do error messages include context?
  • Are exceptions / error codes / return values used consistently?
  • Ask: “What happens in production if this fails?”
Input Validation
  • Ask: “What happens if the user provides invalid config?”
Concurrency Safety
  • Ask: “Is this concurrency safe?”
Style Consistency Across Languages
  • Ask: “Is this consistent with the rest of the codebase?”
When you’re unsure whether tests are good
  • Do tests verify one behaviour at a time?
  • Do they cover failures?
  • Do they cover edge cases?
  • Do they cover configuration variations?
  • Do they use realistic inputs?
When you’re unsure whether to approve
  • If you understand the intent, the consequences, and the tests, you can approve.
  • If any are unclear: ask for clarification before approving.
